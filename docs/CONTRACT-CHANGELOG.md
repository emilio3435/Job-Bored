# Contract changelog

Human-readable history of changes to **[AGENT_CONTRACT.md](../AGENT_CONTRACT.md)**, **[schemas/](../schemas/)**, and **[examples/](../examples/)**. For the roadmap (fixtures, CI, pipeline schema), see **[CONTRACT-HARDENING-PLAN.md](CONTRACT-HARDENING-PLAN.md)**.

| Date (UTC) | Change                                                                                                                                                                                             | Compatibility                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| 2026-09-25 | DiscoveryRuns header read (BEAUDIT D13, `docs/INTERFACE-DISCOVERY-RUNS.md`): only `400` "Unable to parse range" creates the tab; `401`/`403`/`429` no longer fire `addSheet` and a false `tab_created`. A legacy 9-column tab is migrated with its rows (empty `Leads Updated` inserted at G) instead of getting the new header over old rows. Header labels are unchanged. | Additive — fixes misread legacy rows; no column changes. |
| 2026-09-25 | Expired cleanup write semantics (BEAUDIT D2, D3, D9, D10 worker half): an expired row now also clears Follow-up Date (P), matching `/pipeline-update` `stage: "Expired"`. The pass flushes every 25 rows, checks four postings at a time, skips rows checked in the last 7 days (`recently_checked`), and re-reads rows by Link before each write, so a row moved to Applied mid-pass is no longer reverted (`status_changed`) and a deleted row no longer shifts the write onto its neighbour (`row_moved_or_removed`). Result JSON shape is unchanged; the new `reason` strings are additive. | Additive for readers of the cleanup report; P is now cleared on Expired rows. |
| 2026-09-25 | **pipeline-update v2** (BEAUDIT D6, D7, D8, D10): new `schemas/pipeline-update-request.v2.schema.json` and `examples/pipeline-update-request.v2.json` (`npm run test:pipeline-update-contract` checks both versions and the v2 rejections). `stage: "Applied"` requires `appliedDate` and `source`; `appliedDate` and `lastContact` must be `YYYY-MM-DD` (v1 schema tightened to match the parser). Stage moves apply the `pipeline-transitions.js` side effects (Applied Date, Follow-up, audit note; Expired clears Follow-up). The worker answers `409 header_mismatch` when row 1 no longer matches `schemas/pipeline-row.v1.json` (it used to write the wrong columns and return 200) and `409 ambiguous_match` when the job matches more than one row (it used to patch the first). Concurrent updates to one Sheet are serialized, so two note appends both land. Error bodies gain `{error, code, detail, nextStep, retryable}`; `ok` and `message` remain. Success bodies add `matched` and `rowNumber`. | Breaking for v2 senders of Applied without a date and source, and for any sender of a free-text date (now `400`). v1 bodies are otherwise still accepted. |
| 2026-09-25 | Pipeline column ownership and write integrity (BEAUDIT D1, D2, D4, D5, D12, D17, D18, D19): `schemas/pipeline-row.v1.json` gains a per-column `discoveryMerge` rule (`overwrite`, `lockable`, `fillIfEmpty`, `preserve`) and a top-level `discoveryMergeSemantics` legend; the worker column map `integrations/browser-use-discovery/src/sheets/pipeline-columns.generated.ts` is generated from it and `npm run test:pipeline-contract` fails when they differ. Re-discovery now keeps user-edited Source, Priority, Tags, Fit Assessment and Talking Points (fill-if-empty) and writes only changed cells. The worker writer holds a per-Sheet lock, re-resolves rows by Link before writing, re-reads column E before appending, formula-escapes text cells, retries 429/5xx with backoff, runs the append even when the update phase fails, and reads only identity columns for matching. Header labels, column letters and enums are unchanged. | Additive — schema descriptor fields only; no column moves. Re-discovery no longer overwrites non-empty F, I, J, K, Q. |
| 2026-09-25 | Cloudflare relay caller authentication (BEAUDIT G1/G24): `templates/cloudflare-worker/` now requires the per-dashboard `RELAY_TOKEN` as `Authorization: Bearer <token>` (or `X-Relay-Token`) on every request and answers `401` without it, including when no token is configured. It forwards POST only to `/`, `/webhook`, `/discovery`, `/discovery-profile`, `/ingest-url` and `/cleanup-expired`, and GET only to `/runs` and `/runs/<id>`; other paths are `404`, other methods `405`, and the `?target=` override is removed. The POST body is unchanged (`schemas/discovery-webhook-request.v1.schema.json` still validates it, `schemaVersion` 1); the new requirements are transport (a header and a route allowlist on the relay), recorded in the `AGENT_CONTRACT.md` receiver checklist. Anyone who sends an `examples/` body to a relay URL must add the bearer header: `examples/README.md` splits its commands: the relay `curl` and `npm run test:discovery-webhook` commands post only to `$RELAY_URL` and send `Authorization: Bearer $RELAY_TOKEN` (and `RELAY_TOKEN=` for the verify script), say where the token lives, and warn to send it to no other receiver, while the generic-receiver commands (Apps Script, webhook.site, local echo) carry no bearer, and `schemas/discovery-webhook-request.v1.schema.json` gains a `$comment` that relay transport requires the bearer (no schema keyword or body change). `deploy-cloudflare-relay.mjs` mints the token (kept across redeploys of the same Worker, `--rotate-token` to replace it) and stores it only in the owner-only `.jobbored-relay/credential.json` (never in `discovery-local-bootstrap.json`); the dashboard reads it from the loopback-guarded `GET /__proxy/discovery-relay-token`. The run-status poll sends the same bearer, and `npm run test:discovery-webhook` sends `RELAY_TOKEN` (or `--relay-token`) as one. | Breaking for relay callers — anonymous POSTs to a redeployed relay now get `401`; the request body contract and `schemaVersion` 1 are unchanged. Hosted mode is documented as unsupported. |
| 2026-09-16 | `allowUnrestrictedFallback` on an unmatched `companyAllowlist` now seeds this run from the requested names when the stored **active** company list and history are empty (post-wizard local installs). Previously the fallback kept `companies: []` and scouted unrestricted with a blank company, so Companies Seen stayed 0 even though the dashboard sent real names. Seeds are ephemeral; `worker-config.json` is not written. Schema version stays 1. | Behavioral clarification of the existing escape hatch — senders that already set `allowUnrestrictedFallback: true` (the dashboard) now get company-scoped search instead of a blank-company scout. Fail-closed (omit/false) is unchanged. |
| 2026-08-31 | Effective discovery intent (F1-C): worker parser now preserves `mergedUserProfile` (strips resume/secret keys); `discoveryProfile.groundedWebEnabled` is a documented per-run opt-out that is authoritative in effective-source resolution; `companyBlocklist` is subtracted from ATS and normal pools after skip/allowlist; unknown `companyAllowlist` entries no longer silently broaden — unmatched lists are `blocked_unresolved` unless `allowUnrestrictedFallback` is explicitly true; blank-intent guards treat `searchPlan` / `profileSnapshot` / master Fit Profile as intent. Schema + `examples/discovery-webhook-request.v1-with-profile.json` updated together. Grouped multi-Sheet worker-config envelopes round-trip via `applySheetConfigMutation` (unknown fields and sibling sheets preserved). | Behavioral hardening — `schemaVersion` remains 1, but v1 senders with an unmatched non-empty `companyAllowlist` now receive `400` unless they explicitly set `allowUnrestrictedFallback: true`. |
| 2026-06-18 | Added the **pipeline-update** contract: `schemas/pipeline-update-request.v1.schema.json`, fixture `examples/pipeline-update-request.v1.json`, worker endpoint `POST /pipeline-update`, and `npm run test:pipeline-update-contract` (wired into `test:contract:all`). Lets an external agent advance an existing Pipeline row (Status, Contact, Notes, Last contact, Did they reply?) from inbound signals; matched by job URL with company+title fallback; local-first auth via `x-discovery-secret`; writes use the worker's own Google credential. | Additive — new interface contract; existing receivers unaffected. |
| 2026-06-04 | Documented the optional **`mergedUserProfile`** top-level field on the discovery webhook request. It was already sent by the dashboard (`discovery-readiness.js`) and typed in `contracts.ts`, but was missing from the schema and `AGENT_CONTRACT.md`. Non-secret (no raw resume text); validated via ajv and never persisted. | Additive — field was already optional; documentation/schema now match the wire. |
| 2026-05-26 | Added optional `trigger`, `discoveryProfile.profileSnapshot`, and `discoveryProfile.searchPlan` to discovery webhook v1. The trigger enum covers manual, browser-tab, local, GitHub, Cloudflare, Apps Script, and CLI origins. The snapshot records non-secret current profile/resume/preferences/schedule metadata, and the search plan carries the deterministic rotated query bundle used by manual and scheduled runs. | Additive — fields are optional and old receivers can ignore them. |
| 2026-05-20 | Documented hosted discovery run status polling: hosted `/runs/:runId` endpoints require the returned `statusPath` with its per-run `statusToken`, or an equivalent `x-run-status-token`/webhook secret. Browser clients and relays must preserve the returned `statusPath` exactly, including query parameters. | Additive — async webhook acknowledgements remain compatible; hosted status polling is explicitly authenticated. |
| 2026-05-20 | Added `Expired` as a Pipeline status enum and documented safe expired-job cleanup semantics: move confirmed closed rows to column M `Expired`, append audit details to Notes, and never delete rows. | Additive — existing statuses and columns remain valid. |
