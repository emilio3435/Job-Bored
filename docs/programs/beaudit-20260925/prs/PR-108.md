fix(discovery): Partial-with-zeros runs now show why in Error

## What this changes

A manual discovery run that finishes with **Partial**, **0 companies / 0 leads / 0 updated**, and a **blank Error** was not a swallowed crash. The worker completed, wrote a DiscoveryRuns row, and threw away the warnings that explained the zeros.

The Daily Brief Error column now shows the first warning, sheet-write failure, or lifecycle reason. Greenfield workers that still have the shipped ATS example seeds (Scale AI, Figma, Notion) and no user companies also get an explicit warning instead of looking like a silent no-op — only when an ATS lane is actually enabled.

## Why

Two Wednesday 11:41–11:42 AM America/Chicago manual runs (`5dc2afe5b8667fa6`, `8df3036921415e00`) matched this code path exactly:

1. **0 companies** is `config.companies.length`. After onboarding / local wizard (see PR #104), that list stays empty until a `/discovery-profile` refresh persists companies. Variation IDs are random 16-hex keys from `generateDiscoveryVariationKey()` — not a bad config id.
2. **Partial** means “0 leads **and** at least one warning.” Clean empty runs are logged as Success. These runs had warnings.
3. **Error was blank by construction.** `runDiscovery` only filled Error on a Pipeline `writeError`. `buildCompletedRunStatus` never copied `warnings` or `lifecycle.reasonMessage`. The INTERFACE contract already said Error is blank only on success.
4. **~2m 42s** is a finished worker run, not the 60-minute safety timer. Default per-source timeout is 60s; scout + exploit (and ATS against the built-in seeds) lands in that window.
5. **Funnel Last 30 Days all zeros** is consistent: no Pipeline writes, so there is nothing to count. Cover-letter / resume writer is a **separate** path and did not cause this.

Likely greenfield combo, not a sheet-permission failure (a write failure would have been `failure` with a sheet message):

- No stored target companies yet
- ATS still searching the shipped Scale AI / Figma / Notion seeds
- Grounded web running unrestricted from onboarding roles, then timing out, skipping Gemini `google_search`, or dropping LinkedIn/Indeed hits as hint-only

## How

- `formatDiscoveryRunLogError()` is the single Error-column builder for `runDiscovery`, status-derived rows, and `buildCompletedRunStatus`.
- New warning when `companies` is empty, `atsCompanies` is exactly the built-in trio, **and** an ATS source is in `effectiveSources`.
- `lifecycle.companyCount` stays `config.companies.length` so unrestricted-run telemetry (VAL-LOOP-CROSS-001) is unchanged.

## How to re-run and what Success looks like

1. Pull this branch (or wait for merge), restart the local worker (`npm run discovery:worker:start-local` or `npm run dev`). Confirm Tailscale/tunnel still reaches it.
2. In Settings → Profile (or Companies), refresh companies from the fit profile, **or** add real target companies. Do not expect the shipped Scale/Figma/Notion seeds to match a new profile.
3. Check `~/.jobbored/browser-use-discovery/.env` (see `integrations/browser-use-discovery/.env.example`):
   - `BROWSER_USE_DISCOVERY_GEMINI_API_KEY` — grounded Google Search
   - chat LLM key (`BROWSER_USE_DISCOVERY_OPENROUTER_API_KEY` or `BROWSER_USE_DISCOVERY_LLM_API_KEY`) — company refresh / matching
   - optional `SERPAPI_API_KEY` — Google Jobs lane
   - Browser Use command or `BROWSER_USE_API_KEY` — extract beyond search snippets
4. Click **Run discovery**. A new 16-hex variation key is normal.
5. **Success** looks like Status `Success`, Companies **> 0** (after a company refresh), Leads New or Leads Updated **> 0** if those companies are hiring, Error blank.
6. If it is still Partial, Error should now name the cause (empty companies / built-in seeds, missing Gemini tool, Browser Use unavailable, scout timeout). Fix that, then run again.
7. Worker logs: dashboard-started `worker.log` or `~/.jobbored/browser-use-discovery/` — look for `discovery.run.completed` `warnings`.
