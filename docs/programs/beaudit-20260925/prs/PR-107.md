#107 cursor/discovery-partial-empty-error-5525
fix(discovery): Partial runs write a reason into DiscoveryRuns.Error

<!-- CURSOR_AGENT_PR_BODY_BEGIN -->
## What this changes

A finished discovery run that is **Partial** with **0 companies / 0 leads** no longer lands in the Discovery runs modal with a blank Error cell (`—`). The worker now writes the classified reason (or first warning) into `DiscoveryRuns.Error`, counts ATS seeds as companies seen, and stops labeling ATS-only seeds as “no companies configured.”

## Why

Triage of two local manual runs (~11:41 and ~11:42 AM CT, ~2m42–2m44s, `SOURCE=worker`, `STATUS=Partial`, all counts zero, Error `—`):

- **Partial is not a crash.** Worker lifecycle `empty` → sheet `success`; lifecycle `partial` (zero leads **and** any warning) → sheet `partial`; `writeError` → `failure`.
- **Error was blank by construction.** `runDiscovery` already computed `reasonMessage` / warnings, but the DiscoveryRuns logger only copied `writeResult.writeError`. The contract says Error should have a short reason when status is not success.
- **COMPANIES=0 can be a counting lie.** `companiesSeen` used only `config.companies.length`, so default / ATS-only seeds (`atsCompanies`: Scale AI, Figma, Notion) showed as 0.
- **Zero leads after ~2.5 minutes is an expected empty-seed path**, not a watchdog kill (that is 60 minutes). Typical shape: empty `companies` after onboarding persist, unrestricted grounded scout (60s) + exploit (`maxRuntimeMs` 180s) and/or ATS host-search fallback. Missing Gemini / Browser Use / SerpApi keys degrade to warnings, not `failure`.

This PR does **not** rewrite the discovery engine. It makes Partial honest so the next local run tells you *why* it wrote nothing.

## How

- `resolveDiscoveryRunLogError()` fills Error from write error → explicit error → `lifecycle.reasonMessage` → first warning.
- `countConfiguredCompanies()` uniques `companies` + `atsCompanies` for `companiesSeen` / `companyCount`.
- “No companies are configured” warning only fires when **both** lists are empty.
- Browser tracker also reads `lifecycle.reasonMessage` so the Partial toast is not generic.

## Local Mac checklist (config/data — no secrets)

After pulling this branch **or** before it, to get a **non-zero** run:

1. `curl -s http://127.0.0.1:8644/health` — confirm `readiness.ready`, `companiesConfigured`, `atsCompaniesConfigured`, `plannerSeedReady`, Gemini / Browser Use / SerpApi badges. Do not paste keys.
2. Open `~/.jobbored/browser-use-discovery/worker-config.json` and confirm `companies` or `atsCompanies` is a real list (not `[]`). Onboarding `/discovery-profile` persist of an empty company list **clears** the default Scale/Figma/Notion ATS seeds.
3. Confirm the worker `.env` has Gemini (grounded web) and ideally `SERPAPI_API_KEY` (highest-ROI lane per SETUP.md). Keys stay in the ignored env file.
4. In the Discovery drawer, set target roles / keywords, then **refresh companies** so the worker has seeds. Or add 3–5 employers that use Greenhouse/Ashby/Lever.
5. Re-run discovery. A clean zero-match run should be **Success** (empty), not silent Partial. A degraded run should show a short Error (timeout, missing Gemini tool, weak seed, etc.).
6. Worker logs: `discovery.run.config_resolved` (company lists + `effectiveSources`) and any `*_timeout` / `grounded_*` warnings.

## Anything reviewers should look extra carefully at?

`companiesSeen` semantics now include `atsCompanies`. That matches what the run actually searched on a fresh worker. `INTERFACE-DISCOVERY-RUNS.md` is updated; this is not a Pipeline-column or webhook-schema change.
